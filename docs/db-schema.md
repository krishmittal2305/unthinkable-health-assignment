# Database Schema

PostgreSQL via Prisma. Full source of truth is [backend/prisma/schema.prisma](../backend/prisma/schema.prisma);
this is a narrative guide to it, organized by area rather than declaration order.

## Identity

**User**: `id, email (unique), passwordHash, name, role (PATIENT|DOCTOR|ADMIN), phone?`. One table for
all three roles; `role` gates what a JWT can do (see `middleware/auth.js`). Patients self-register;
doctor/admin accounts are only created by an existing admin (`POST /api/auth/admin/users`).

**DoctorProfile**: one-to-one with a `DOCTOR` user. `specialisation, workingHours (JSON, e.g.
`{"mon": ["09:00","17:00"]}`), slotDurationMins`. The availability engine derives bookable slots for a
date purely from this JSON plus existing bookings; no separate "schedule" table.

**LeaveDay**: `doctorId, date (UTC midnight), reason?`, unique on `(doctorId, date)`. A row here blocks
that whole day from `workingHours` and triggers the cancellation cascade in `leaveService`.

## Booking

**SlotHold**: `doctorId, patientId, slotStart, slotEnd, expiresAt`, unique on `(doctorId, slotStart)`.
A short-lived (5 min) claim on a slot while the patient fills the symptom form, before it becomes a real
`Appointment`. Cleaned up opportunistically and by a per-minute cron sweep.

**Appointment**: `patientId, doctorId (→ DoctorProfile), doctorUserId (→ User, denormalized for direct
doctor-side queries without an extra join), slotStart, slotEnd, status, reminderSentAt?`.
`status` is one of `BOOKED, COMPLETED, CANCELLED_BY_PATIENT, CANCELLED_BY_DOCTOR, CANCELLED_BY_LEAVE,
NO_SHOW`. Indexed on `patientId` and `(doctorId, slotStart)`.

Deliberately **no** `@@unique(doctorId, slotStart)` in the Prisma schema (see the partial-index note
below). `reminderSentAt` makes the appointment-reminder cron idempotent regardless of how often it runs.

### The double-booking guard

A raw-SQL migration (`20260823092211_drop_full_unique_appointment_slot`) adds:

```sql
CREATE UNIQUE INDEX "Appointment_doctorId_slotStart_active_key"
  ON "Appointment" ("doctorId", "slotStart")
  WHERE "status" IN ('BOOKED', 'COMPLETED');
```

A plain unique constraint would let a single cancelled appointment permanently occupy that
`(doctorId, slotStart)` key, blocking the slot from ever being rebooked. The partial index only enforces
uniqueness among rows that actually occupy the slot going forward, so cancelling frees it immediately,
while still giving Postgres an atomic collision point for concurrent booking attempts.

## Pre-visit

**SymptomForm**: one-to-one with `Appointment`. `symptoms (free text), durationDays?, severity?`,
collected as part of `confirmBooking`.

**PreVisitSummary**: one-to-one with `Appointment`. `urgencyLevel (LOW|MEDIUM|HIGH), chiefComplaint,
suggestedQuestions (JSON string[3]), rawLlmResponse?, isFallback`. Generated by `llmService` right after
booking commits; `isFallback: true` means Azure OpenAI was unavailable/misconfigured/returned something
unparseable and a safe default was substituted instead.

## Post-visit

**PostVisitNote**: one-to-one with `Appointment`. `doctorUserId, clinicalNotes`, submitted when the
doctor completes the visit (which also flips `Appointment.status` to `COMPLETED`).

**Prescription**: many-to-one with `PostVisitNote`. `drugName, dosage, frequency (free text, e.g.
"twice a day"), durationDays`.

**MedicationReminder**: many-to-one with both `Appointment` and `Prescription`. `remindAt, sent`. Rows
are generated from a prescription's `frequency` string by `medicationScheduler.js` (a simple heuristic
parser: fixed daily clock-times or a fixed hourly interval) and dispatched by a 5-minute cron sweep.

**PostVisitSummary**: one-to-one with `Appointment`. `summaryText, medicationPlan? (JSON), followUpSteps?
(JSON string[]), rawLlmResponse?, isFallback`. Same LLM-with-fallback contract as `PreVisitSummary`.

## Notifications & Calendar

**NotificationLog**: `channel (EMAIL|CALENDAR), type, recipientId, subject?, payload (JSON), status
(PENDING|SENT|FAILED), retryCount, lastError?`. Every outbound email is logged here *before* it's
attempted, so intent survives a crash or an outage at the email provider. A cron job retries `PENDING`/`FAILED` rows with
exponential backoff up to `MAX_RETRIES`.

**GoogleCalendarToken**: one-to-one with `DoctorProfile`. `accessToken, refreshToken, expiryDate`.
Only doctors connect via OAuth; patients are added to the resulting Google Calendar event as an
attendee by email, so they get an invite without a second OAuth flow.

**CalendarEvent**: one-to-one with `Appointment`. `googleEventId`, used to update/delete the linked
Google Calendar event on cancellation.

## Cascade behavior

Foreign keys from child records (leave days, holds, appointments, notes, etc.) to `User`/`DoctorProfile`
use `onDelete: Cascade`. In practice, deleting a doctor is blocked in the service layer
(`doctorService.deleteDoctor`) whenever they have a `BOOKED`/`COMPLETED` appointment, specifically to
avoid the cascade silently wiping active appointment history; leave days are the intended tool for
taking a doctor out of future rotation instead.
